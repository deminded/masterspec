# Рабочая зона и пробная проекция

Читай при подготовке или продолжении импорта. Завершённый импорт сначала проверяется
на read-only no-op по review-policy; ради него рабочая зона не создаётся.

## До первого лога

Разреши source/factory/specs/destination без записи. Затем:

```text
python <skill-dir>/scripts/prepare_workspace.py init --change <destination> --factory <factory> --source <source> --specs <native-specs-root>
```

Помощник создаёт отдельный `<destination>/.work/<run>/` и возвращает JSON с
`workspace` и разрешёнными корнями записи. Для занятого destination проверяется
происхождение; чужой change и прежние runs не перезаписываются. Необязательный
`--run <slug>` выбирает имя нового run, но не произвольный путь.

До init вывод остаётся в ответах инструментов. После init все логи, скрипты,
частичные review и проекции — в выданном work_root; итоговые change/map/review —
в destination. Не используй общий `.work` фабрики или соседнюю временную папку.
Иной путь итогового отчёта допустим, если его явно задал пользователь.

Каждому делегату передай абсолютные read roots, его конкретные output paths и
work_root из JSON. Указанная вызывающим рабочая зона имеет приоритет над default
путями evolve/verify. Делегат возвращает список созданных файлов; оркестратор
проверяет разрешённые пути до принятия результата. В harness с filesystem sandbox
ограничь делегату запись этими путями. Сам helper проверяет только собственные
операции: он не изолирует произвольные shell-команды и не предотвращает чужие записи.

## Один механизм проекции

После подготовки определённых diff:

```text
python <skill-dir>/scripts/prepare_workspace.py project --workspace <workspace.json>
```

Получатся `baseline/`, `after/` и `projection.json` внутри того же run. Они не
перезаписываются: после исправления change создай новый run. Оба среза содержат
одинаковый разрешённый scope: `01/02/04`, словарь, индекс и объявленные сайдкары.
Код, codemap, native specs, changes и рабочие каталоги не копируются.

Поддерживаются `modify-bullet`, `replace-section`, `add-subsection`, ADDED/REMOVED
и замены authored-сайдкаров. Сопоставление строгое в указанном разделе; неоднозначный
якорь, несовпадающий ДО у `modify-bullet`, устаревший snapshot или неподдерживаемый
`set-frontmatter` дают ошибку. Не ослабляй diff ради прохождения проектора.
У `replace-section` ДО — история review, не условие замены: как в canonical apply,
от дрейфа защищают snapshots. Неизвестные операции не исполняются.
Внешний/необъявленный владелец изменяемого сайдкара также требует отдельного процесса.

Структурные import/scope gates обязательны. Семантический `blocked` допускает
проекцию записанной части черновика для диагностики; он сохраняет силу и не даёт
готовности к apply. Если нужная операция не поддержана или проекция не завершилась,
укажи ограничение проверки; не называй частичный каталог после-состоянием.

Это **проекция текста для review**, без смены статуса/updated, сертификации,
синхронизации native main или production apply. Индекс остаётся копией baseline;
это явно указано в projection.json. Для проверки индекса выполни spec-only reindex
в after отдельным шагом и отрази его в review. Production apply сохраняет свой
lifecycle, rollback и обязательный reindex в `masterspec-apply-change`.

Сравнивай baseline и after одинаковыми детекторами из review-policy. Копирование
двух равных срезов устраняет ложные расхождения числа файлов из-за исключения codemap.

## Сохранение доказательств

Рабочие материалы импорта сохраняются, пока на них ссылается review, открыт
блокер или нужен повторный прогон. Перед чисткой перенеси необходимые результаты
в итоговый отчёт и обнови ссылки. Не удаляй `.work` автоматически по общему правилу
verify: для импорта действует эта политика. Удалять можно только свой run после
проверки абсолютного пути; чужие runs и пользовательские материалы сохраняются.
