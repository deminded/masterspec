# Готовность переноса и работа с находками

## До change: отдели исходное состояние от дельты

Подготовь одинаковые срезы baseline/after через [workspace.md](workspace.md).
На обоих запусти `check-layout.py --check` и `check-operational-envelope.py`
с `--layer req`, затем `--layer spec`; дополнительные детекторы — по затронутым типам.
Не сравнивай полную фабрику со срезом без codemap. Нормализуй только префиксы корней
в локаторах; не удаляй ошибки по их количеству. Индекс проекции пока копия baseline:
проверка его после-состояния требует отдельного reindex в разрешённом scope.
Проекция blocked-черновика показывает только записанные diff, не неизвестное решение.

Сравнивай находки по правилу, артефакту и AC/OE, а не только числу BLOCKER:

| Находка | Решение |
|---|---|
| Существовала до change и не усиливается им | `baseline-debt`: включить в review и остаток сертификации; сама по себе перенос не блокирует |
| Новая/усиленная дыра, потерянный сценарий, висячая ссылка | Исправить дельту; до исправления `cascade_ready: no` |
| Для переноса обязательна цель, которую нельзя корректно изменить/индексировать в текущей схеме | Блокер применения; отдельная миграция или согласованное исправление формы, без молчаливого пропуска |
| Неизвестно поведение, критичность нового TC или выбор между нормами | `blocked`, вопрос владельцу; норму и значение по умолчанию не изобретать |
| Сломан чужой OpenSpec change | `layout-health`/baseline-debt; проверить выбранные source и destination отдельно |

Старый долг не освобождает НОВЫЙ артефакт от обязательных полей. Если новый TC
требует criticality, а владелец функции её не определил, это недостающие вводные.
Нельзя обходить gate исключением нужного API из change или угадывать `scope`
из legacy `direction` (включая `provided` и `internal`). Полная сертификация проверяет
всю фабрику и при сохранённом долге остаётся неполной, даже если перенос готов.

## Решение автора и вопрос владельцу

Сначала проверь каждую находку verify по исходным текстам. Исправляй самостоятельно
то, что однозначно выводится из норм: потерянный сценарий, ошибочную ссылку,
несогласованный oracle, неполную §2/§4/§5, отсутствующий вердикт соседу.
Повторно проверяй изменённую часть. Не откладывай независимые механические исправления
до ответа владельца. Если правка зависит от ответа, сохрани вопрос и зависимость.

Сверяй каждый native WHEN/THEN с oracle по [mapping.md](mapping.md), а не только
с совпадением чисел и терминов. Утверждение «когда ответ получен, он содержит X»
проверяет качество полученного ответа, но не гарантирует приём входа и получение
ответа. Отсутствие TC в baseline не делает новый непокрытый исход старым долгом.

Для конфликта укажи две точные нормы и общий случай, в котором они требуют
несовместимых исходов: участник, вход, условие и момент наблюдения. Общая тема
или слово «длина» конфликт не доказывает: предупреждение о длине, отказ в приёме
и наблюдение целостности могут действовать одновременно. Недоказанное подозрение —
вопрос проверки, а не подтверждённое противоречие. Accepted ADR нельзя молча
перекрыть поведением из source; выбор владельца отражается в исходной норме/решении.

**Следствие или выбор.** Самостоятельно переноси только вывод, однозначно следующий
из source и сохраняемых норм для того же входа и условий. Сверь момент, канал и
состав ответа, квитанции и побочные эффекты: одинаковый итог «не отправлено»
не доказывает эквивалентность синхронного отказа и последующего события.
В спорном месте запиши короткую цепочку: `общий вход → source → сохраняемая норма
→ вынужденный вывод / различимые варианты`, с локаторами оснований.

Если надо выбрать приоритет, сузить независимое обещание, убрать/перенести ответ
или изменить accepted ADR — это выбор владельца. Прецедент другого отказа и
отсутствие готового носителя ответа не разрешают отменить обязанность сообщить его.
Например, «нота только в квитанции принятой команды» позволяет не выдавать её при
отказе; «нота при каждой подаче» такого исключения не содержит.
Не усиливай норму: «не ставить в очередь» само по себе не запрещает формирование
команды. Несколько внутренних способов с одинаковыми нормативными наблюдениями
не являются блокером и не требуют выбора реализации в этом скилле.

Purpose/proposal помогают найти область нормы, но не сужают явное SHALL/AC.
Отсутствие верхнего предела в одном файле ещё не доказательство конфликта:
проверь остальные ограничения. Доказательство — разрешённый базой случай,
нарушающий новое требование; неполные основания оставь вопросом проверки.

`REMOVED` не отменяет инварианты мета-модели. Если исчезает единственный AC
обязательной OE-грани, спроси владельца о новой норме либо сохранении неизвестности:
`OPEN` у грани, `draft` у артефакта — это разные статусы.
OPEN фиксирует неизвестность и блокирует готовность; это не автоматическое
разрешение применить неполный контракт. Не вписывай один из вариантов в ПОСЛЕ
как будто он уже выбран.

## Статус и отчёт

Пока строится change — `Черновик`. Есть нерешённый блокер — `Заблокировано`;
его ID и краткая причина видны в шапке change и в import-review. Определённые
части можно сохранить как черновые diff; неизвестная операция остаётся в map
как `blocked`, без выдуманного ПОСЛЕ. Частичную определённость отражай по
[mapping.md](mapping.md), без нового disposition. Если определённых diff нет,
достаточно inventory/map/review, пустой канонический change не нужен.

В шапке используй отдельную строку `> **Блокеры**: <ID — причина; ...>`;
не дописывай причины к значению `Статус`.

Только после структурных gates и семантического review без блокеров переноса
ставь `На согласовании`. `Согласовано` опирается на разрешение пользователя,
включая действующее условное предразрешение по `masterspec-apply-change` §2.1.
Смена одного статуса не снимает `blocked` в карте. Прямой вызов apply-change
тоже обязан проверить карту и ревизии источника.
После ответа владельца обнови нормы/карту и зависимые diff, верни статус в `Черновик`
для повторных gates. `На согласовании` наступает по их результату, не по наличию ответа.

В `import-review.md` достаточно следующих сведений:

- source, native specs-root и destination (пути для повторного gate; не команды);
- покрытие по таблице ниже;
- scope-fence: `сосед | локатор | changed / unaffected / blocked | основание`;
  известные нижние рёбра — только `deferred-to-implementation`;
- baseline-debt, новые/усиленные дефекты, вопросы владельцу и исправления;
- результаты gates, независимость проверки, готовность и ограничения apply.

Для покрытия используй компактную таблицу; несколько строк могут ссылаться на один AC:

| Source: operation ID, путь и точное имя requirement/scenario | WHEN / канал / вход | Наблюдаемый THEN и запрещённые эффекты | Цель: AC/проверка с локатором | Вердикт и основание |
|---|---|---|---|---|

Сверь множество имён scenarios с inventory: без пропусков и придуманных названий,
с учётом `before`/`after` и семантики операции по mapping.
Условия полного requirement, не исчерпанные примерами, отрази отдельными строками
с локатором requirement. Для `already-satisfied` предъяви существующий oracle;
предусловие, отсутствие запрета или ссылка на весь файл доказательством не служат.

Для gate запиши команду, версию инструмента, проверенный source/inventory_id,
exit code и путь к логу в `work_root`. `status` и прежний PASS без привязки к ревизии
не заменяют `validate --strict`. Обязательный доступный gate, который не запускался
или упал, оставляет готовность заблокированной. Недоступный CLI/detached export
описывай как `not-run` с причиной по SKILL §2, без вымышленного PASS.

Если новый прогон изменил прежний вердикт, укажи найденную норму, изменённую
ревизию или ошибку прежнего вывода. Уверенность другого исполнителя основанием
не является; существенный спор проверь независимо на исходных нормах.

Scope-fence живёт в review (или в route-run, на который review ссылается),
не дублируется в change.md. `target_files` включает все цели, индекс и файлы,
чьё содержимое обосновывает mapping **или unaffected-вердикт**. Поисковый hit
без использования его содержания не требует snapshot, но не является
доказательством отсутствия влияния. Перед apply повтори discovery соседей:
хеши известных файлов не обнаруживают новые зависимости сами по себе.

Вердикт соседу учитывает все связанные операции, включая ADDED/REMOVED, а не только
замену числа. Для `rules` и других сквозных норм укажи точный пункт и объясни, почему
он требует правки или остаётся верным. Правило «проверять длину» само по себе не
запрещает проверку непустоты; отсутствие новой проверки в таком тексте не доказывает
противоречия. Если действующая норма уже охватывает новый случай или не задаёт полный
перечень проверок, обоснуй `unaffected` без дублирования нормы. Если нужный исход
отсутствует в её обязательной области, внеси каскадную правку; не переноси вердикт
другого прогона без сверки исходного пункта.

## Независимость проверки

Независимый контекст — отдельный исполнитель, получивший задачу, сырьё и критерии,
без авторского вердикта/ожидаемого ответа. Он заново считает каскад. Та же модель
допустима; в отчёте отдельно укажи изоляцию контекста и разнообразие моделей.
Та же модель не даёт независимости ошибок. Один исполнитель в том же контексте —
self-review. Для малого change допустим один проверяющий на весь каскад с единым
отчётом; поузловая декомпозиция нужна при большом фокусе, а не ради числа вызовов.

После механической правки достаточно повторить затронутый детектор и отметить
self-review. Смена смысла, границы нормы или каскада требует повторной независимой
проверки этой части. Отчёт упавшего исполнителя — частичное свидетельство: его
находки можно перепроверить, но он не закрывает порученный scope без явного
подтверждения полноты другим проверяющим. Разнообразие моделей не обязательно;
не называй его состоявшимся по одному запущенному, но незавершённому вызову.

Для независимого пересчёта сначала передай сырьё и критерии без авторского вердикта.
Затем дай полный candidate для сверки, включая явно не завершённые части. Не удаляй
из него смысловой контекст ради «слепоты»: иначе объявленный остаток выглядит потерей.
Укажи эти две стадии в отчёте; один просмотр candidate — обычное review.

## Применение и две редакции спецификации

Prepare разрешён вне Git. Production apply требует Git worktree с HEAD и точкой
отката для всех существующих целей и индекса. Если её нет, верни готовый change
с блокером применения; не называй пустой вывод неуспешного `git status` чистотой.
Инициализация/первый коммит допустимы только в уже разрешённом пользователем объёме;
не делай `git add .` над неизвестной копией. Учебный replay во временной папке
не заменяет это условие для чужой фабрики.

Native specs могут соседствовать с деревом MasterSpec внутри `openspec/specs`.
После apply нормативное состояние MasterSpec отражает импортированную дельту,
native main пока отражает прежнюю базу. Запиши в apply-report
`native_sync: pending-owner` и точные capability; это явное ожидание синхронизации,
не потерянный пункт и не свидетельство реализации. Сам импорт native main не меняет.
Sync/archive выполняется отдельно владельцем. При повторе после такой синхронизации
сначала сравни состав и SHA256 source-файлов с `source_files` сохранённого inventory
(без прежних хешей native main). Есть новый/изменённый source — это новая ревизия,
не no-op. Если source тот же, заново сверь постусловия операций, включая требования
и scenarios, с текущими нормами MasterSpec по таблице покрытия; apply-report помогает найти цели,
но не заменяет source. Совпадение after с authored diff, хешей или изменённого числа
доказывает применение записанного change, но не полноту переноса. При изменённом
native main проверь отражение постусловий и там. Совпало — read-only
no-op, не пересобирай pre-apply inventory: MODIFIED/REMOVED уже поглощены native базой.
Не совпало — блокер сверки и отдельный корректирующий change после review,
без перезаписи исторических хешей и повторного apply старой дельты.
