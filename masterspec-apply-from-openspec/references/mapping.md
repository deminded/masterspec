# Контракт переноса

## Семантика операций

| OpenSpec | Изменение MasterSpec |
|---|---|
| ADDED | Новая норма в существующем владельце или новый артефакт. Уже есть эквивалент — `already-satisfied` с доказательством. |
| MODIFIED | Сравнить полный native requirement с базой. Перенести изменённые условия и каждый сценарий, сохранив несвязанные нормы MasterSpec. |
| REMOVED | Удалить соответствующую норму и её зависимые проверки. Весь артефакт удалять лишь когда других обязанностей и живых ссылок не осталось. |
| RENAMED | Обновить существующее отображаемое имя и mapping; сохранить slug и AC ID. Если в MasterSpec нет такого имени, `already-satisfied` с локатором прежней нормы; заголовок ради переименования не создавать. |

OpenSpec scenario с WHEN/THEN — кандидат в AC и `tc-acc`, а не автоматически
`scn-*`: сценарий MasterSpec описывает кооперацию компонентов. Технический контракт
может относиться к `api/data/scn` в `02-`, измеримый предел — к `nfr` в `01-`.
Разделяй слои по смыслу, не по английскому SHALL или имени каталога.

Для каждого native scenario в ADDED/MODIFIED сохрани точное имя и source-локатор и укажи проверяемый
AC/test oracle: существенные условия WHEN, канал и наблюдаемый исход THEN, включая
запрещённые побочные эффекты. Предусловие допустимости входа и отказ для другого входа
не доказывают положительный исход: «не длиннее предела» и «сверх предела — отказ»
не проверяют, что допустимый вопрос принят. Подходящий общий AC можно использовать
с данными source-сценария; сохрани его ID. Дополняй существующий AC или добавляй новый,
только если его oracle не покрывает нужный исход и условия. Один scenario не требует
отдельного AC или файла, но строка mapping без такого покрытия недостаточна.

Покрытие учитывает операцию: для ADDED/MODIFIED сверяй итоговое `after`; для REMOVED —
отсутствие удалённой обязанности и её зависимых проверок, сохраняя проверки других норм.
Для чистого RENAMED подтверждай новое имя и неизменность поведения/AC ID; новые AC
ради переименования не нужны. Сценарии `before` не превращаются в новые обязанности.

Отдельно сверь полный текст requirement: сценарии — примеры, не предел его действия.
Сохрани все каналы, диапазоны и классы входов. Например, `whitespace-only` не равно
«только пробелы», если такая эквивалентность не определена нормами; пример с пробелами
не исключает табуляцию/перевод строки. Требование для одного канала не расширяй на все.
«Принят для обработки» не заменяй на «прошёл проверку длины». Сохраняемые ограничения
учитывай с локаторами оснований, без придуманных предусловий; если они несовместимы
с обещанием source для общего случая, зафиксируй конфликт по review-policy.

Одна операция может затрагивать несколько артефактов; несколько операций — один.
Не создавай файл на каждый requirement. Данные задачи, единицы, границы, отрицательные
исходы и модальность обязательности сохраняются. Недостающая норма — вопрос, не best practice
по умолчанию. Исключённые требования не восстанавливаются из design/tasks.

`Reason`/`Migration` внутри REMOVED сохраняются как обоснование, но сами не вводят
заменяющее поведение. Упоминание перехода polling → push не разрешает переписать
все нормы опроса. Если migration содержит существенное предписание, которого нет
в ADDED/MODIFIED, запроси явную норму в delta. Старые зависимости, затронутые именно
удаляемым обязательством, входят в каскад; совпадение терминов само по себе — не связь.

Владение машинными контрактами сохраняется: импорт OpenSpec сам по себе не является
`adopt` или `reimport` существующего сайдкара. Для таких операций действуют основания
и preflight из `masterspec-apply-change`; неоднозначное владение блокирует перенос.

## import-map.json (schema_version = 1)

```json
{
  "schema_version": 1,
  "inventory_id": "<из source-inventory.json>",
  "bindings": [
    {
      "operation_id": "<точный operations[].id>",
      "disposition": "change",
      "targets": [
        {"path": "01-requirements/02-functions/fn-example.md", "anchor": "AC-01"}
      ],
      "reason": "Норма принадлежит функции; меняется только её предел."
    }
  ],
  "target_files": [
    {"path": "00-masterspec-index.md", "sha256": "<SHA256 сырых байтов>"},
    {"path": "01-requirements/02-functions/fn-example.md", "sha256": "<SHA256>"}
  ]
}
```

`operation_id` берётся из inventory, не из порядкового номера в своём списке.
`disposition`: `change` / `already-satisfied` / `blocked`.
Каждая операция имеет непустое основание; у первых двух — цели с точными якорями.
При `blocked` укажи вопрос в reason; targets может быть пустым, если владелец ещё
не установлен. Apply запрещён целиком, но gate проверяет остальные доступные данные
и возвращает сводные diagnostics; blocked не скрывает структурные ошибки.

Если не определена часть операции или её обязательного каскада, вся binding остаётся
`blocked`: частичной готовности в schema нет. В `reason` назови готовую часть и остаток,
а в review свяжи их с черновыми diff. Однозначно определённые изменения допустимы в
change со статусом `Заблокировано`, даже если все bindings blocked; неизвестный
вариант ПОСЛЕ не подставляй. Наличие такого diff не подтверждает готовность операции.
Установленные владельцы/якоря остаются в targets. Зависимости между операциями
(например, REMOVED допустим только вместе с заменяющим ADDED) фиксируй в review;
частичное применение не разрешается.

`target_files` содержит все цели bindings и §2 change, индекс и прочитанные
зависимости mapping; новый путь — `sha256: null`. Все пути относительно specs-root,
только spec-only и индекс. Нельзя заново хешировать базу вместо разбора конфликта.
Зависимости вердиктов unaffected также фиксируются; границы снимка и scope-fence —
в [review-policy.md](review-policy.md).

Каскадная правка из §2 может не иметь отдельной OpenSpec операции; её необходимость
обоснуй в import-review и включи файл в снимок. Помощник проверяет полноту ID, пути,
хеши и структуру change, но не эквивалентность норм и полноту каскада.

## Источник и повторные запуски

Inventory фиксирует дельты, `.openspec.yaml` и соответствующие native main specs.
Пути capability сохраняются целиком, включая вложенность. Абсолютные пути машины
не входят в identity.

Ответ владельца разделяй на норму и обоснование. Новое поведение, область действия
или определение термина, меняющее допустимые исходы, должны появиться в native delta.
Мотивы и пояснения могут оставаться в source `proposal.md`; зафиксируй их значимую
часть и локатор в `import-review.md`. Они объясняют норму, но не подменяют её и не
расширяют разрешённый каскад. Изменение accepted ADR требует явной согласованной
цели изменить это решение; меняющий поведение выбор должен быть выражен в native delta.
Одним обоснованием в proposal нельзя отменить действующее решение. Происхождение ответа хранится в review,
а не ссылками на change в нормативном артефакте.

Источник с `skip_specs: true` — MasterSpec/OpenSpec служебный мост, а не native
изменение требований. Повторно импортировать его нельзя. Изменение не архивируется
и не синхронизируется в OpenSpec автоматически: это отдельная операция владельца.

Первый адаптер поддерживает канонический Markdown схемы `spec-driven` и простые
корневые скалярные поля `.openspec.yaml` (например `schema`, `created`). Сложный YAML,
несколько документов, алиасы, links/junctions и нестандартная грамматика отклоняются
с диагностикой. Это явная граница совместимости, не обещание всех custom schemas.
Полную проверку OpenSpec выполняет его CLI; текущий пример проверен на 1.13.2.

Перед повторным импортом ищи совпадающий inventory_id в активных и архивных
отчётах destination-фабрики. Если прежний change применён, заново сверь постусловия
операций, включая полные requirements и scenarios, по таблице покрытия из review-policy.
Совпало — no-op; расхождение — новый review и change,
без молчаливого возврата старой редакции. Исходный snapshot применяется только
до первого apply; после него состояние сравнивается с итоговыми постусловиями.

Если apply ещё не было, это продолжение подготовки: сверь происхождение, inventory
через `--check`, целевые snapshots и gates. При неизменном входе и отсутствии новых
решений верни существующую готовность или те же блокеры, без перезаписи артефактов
ради повтора. Новый ответ или ревизия требуют пересопоставления и review; прежние
хеши не обновляются автоматически. Отсутствие записей не означает no-op: он возможен
только после подтверждённого apply либо для полной карты `already-satisfied` без
блокеров и ожидающих diff, как описано в SKILL §3.
