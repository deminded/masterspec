# Дисциплина слоёв

Применяется к содержимому артефактов и предлагаемых правок, включая diff-блоки, планы,
решения и ответы пользователю. Полная модель — `meta_model.md`, раздел 2.
Граница слоя определяется смыслом текста, а не расширением файла или наличием блока кода.

---

## 1. Три слоя и их границы

| Слой | Вопрос | Директория | Что описывает |
|---|---|---|---|
| **Требования** | ЧТО даёт система и как себя ведёт | `01-requirements/` | Полезность, внешнее поведение, ограничения |
| **Спецификации** | КАК устроено взаимодействие частей | `02-specifications/` | Компоненты, их кооперация, контракты |
| **Кодовая база** | ГДЕ в коде это реализовано | `03-codemap/` | Файлы, классы, строки, таблицы |

**Трассировка и ссылки идут снизу вверх:**
- слой требований НЕ ссылается на спецификации и код;
- слой спецификаций ссылается вверх на требования (и в пределах своего слоя);
- слой кода ссылается вверх на спецификации (и на требования напрямую при необходимости).

Цель: читатель видит цепочку «вот это мы хотим → вот так это происходит → вот так это реализовано», без дублирования между слоями.

## 2. Жёсткие запреты по слоям

### 2.1. В слое требований ЗАПРЕЩЕНО

- имена компонентов, сервисов, модулей (`cmp-*`, «оркестратор», «адаптер»);
- имена физических таблиц, коллекций, индексов и колонок; доменные сущности и их атрибуты допустимы;
- языки, фреймворки, библиотеки, СУБД, брокеры, протоколы (кроме случаев, когда это явное внешнее ограничение бизнеса);
- классы, методы, программные функции, пути исходников и эндпоинты реализации;
- ссылки на `cmp-`, `scn-`, `alg-`, `api-`, `data-`, `cd-`, `lp-`, `tc-int-`, `tc-flt-`, `cmap-`, `trace-`, `dmap-`.

### 2.2. В слое спецификаций ЗАПРЕЩЕНО

- код, псевдокод, имена классов/методов/функций;
- файлы и пути исходников, номера строк, пакеты, namespace;
- конкретные таблицы, колонки, типы СУБД, миграции, ORM-классы;
- конкретные технологии (PostgreSQL, Redis, Kafka, Spring) в телах контрактов и данных — если только это не внешнее ограничение, зафиксированное в ADR;
- ссылки на `cmap-`, `trace-`, `dmap-`.

**В спецификациях допустимы:** архитектурные компоненты и их взаимодействия, операции API
(включая HTTP-метод и путь), имена и типы полей контрактов, логические схемы данных,
машинные сайдкары, декларативные таблицы решений и тестовые сценарии без исполняемого кода.
Пути файлов самих спецификаций и ссылки на их сайдкары также допустимы.
Например, `POST /orders` — адрес операции контракта; `src/orders.py` — путь реализации.
Идентификатор `operationId` описывает операцию API и не предписывает имя метода в коде.

### 2.3. В слое кодовой базы

Привязки к реализации (`file:line`, классы, физические таблицы) — здесь.
Каждый code unit ссылается вверх на slug из спецификации (при отсутствии — на требования).
Проектирование этих правок выполняет `impl-plan`, изменение кода — `implement`.

### 2.4. Граница workflow evolve

`evolve` работает только с `01/02`, словарём `00-glossary.md` и решениями `04`,
которые обосновывают эти изменения. Решение `04` не является обходом запрета на код.
Чтение исходников, `03-codemap/`, кодового research (независимо от пути хранения)
и планов реализации не входит в evolve.
Из уже доступного индекса можно взять slug нижнего соседа и его связь со спецификацией,
не открывая тело codemap; неизвестные нижние зависимости не требуют исследования кода.

На границе `03` каскад останавливается с вердиктом `deferred-to-implementation`.
Отложенная реализация не блокирует полноту каскада требований и спецификаций.
`gen`, planner, verify и любые другие делегаты наследуют границу вызывающего workflow;
доступность инструмента не даёт разрешения расширить её.

| Допустимый результат evolve | Недопустимый результат evolve |
|---|---|
| «Повтор запроса с тем же ключом возвращает прежний результат» | «Добавить проверку ключа в метод `Handler.send`» |
| «В `api-orders` добавить необязательное поле `clientReference`» | «Добавить колонку SQL и миграцию; обновить ORM» |
| «`scn-order`: следующий этап — отдельная реализация» | «План: изменить контроллер, репозиторий и unit-тесты» |

Запрет относится и к рекомендациям в обычном тексте, route-run и финальном ответе.
Исполняемые тесты отличаются от разрешённых спецификаций тестов `tc-acc`/`tc-int`.

## 3. Что где живёт (во избежание путаницы)

- **Use-case** (черновой сценарий в терминах «актор — система») — в функции АС/ФП (`fn-`), не в сценарии.
- **Контракт живой эксплуатации** (объём, реальные формы входа, наблюдаемый след, классы источников,
  безопасность, устойчивость, сквозная доставка, управляющий ввод) — восемь `OE-*` только внутри
  external-I/O `fn-`; internal-only содержит одну N/A-строку. Это внешнее поведение, не алгоритм.
  Сценарий и codemap ссылаются вверх как `-> fn-<slug>/OE-<ID>`.
- **Порядок вызова компонентов** — только в сценарии (`scn-`), не в функции.
- **Функциональность компонента** — в разделе «Возможности» внутри `cmp-` (как `cap-*`). Отдельных файлов на функциональность нет.
- **Алгоритм принятия решений** внутри компонента — в алгоритме (`alg-`), не в функции.
- **Контракт взаимодействия** (вход/выход, ошибки, SLA) — в API (`api-`), не в компоненте.
- **Ключевые справочники/классификаторы** предметной области — в `dict-` (только если малые, стабильные, доменные). Структура полей — в сущности `cdm-`.
- **Приёмочные тесты** (чёрный ящик, проверяют AC функции) — в `tc-acc-`, слой требований.
- **Интеграционные тесты** (проверяют сценарий) — в `tc-int-`, слой спецификаций.
- **Каталог отказов** (точка `scn→api` × модус → результат → tc-int) — в `tc-flt-`, слой спецификаций.

Если сомневаешься — см. `meta_model.md`, раздел 2.

## 4. Направление ссылок

```
КОД          cmap  trace  dmap                              ──► ссылаются на cmp, scn, cdm, data
             ▲     ▲      ▲
СПЕЦЫ        cmp(cap)  scn  alg  data  api  lp  cd  tc-int/tc-flt ──► ссылаются на fn, as, cdm, nfr, rules, dict
             ▲         ▲                                 ▲
ТРЕБОВАНИЯ   as  fn  nfr  rules  context  fd  cdm  dict  tc-acc
```

- Стрелка `▲` = «ссылается на вышестоящий слой».
- Обратных стрелок быть не должно. Если в артефакте требований встретилась ссылка на `cmp-` / `scn-` / `api-` / `data-` / `lp-` / `tc-int-` / `tc-flt-` / `cmap-` / `trace-` / `dmap-` — это ошибка, убрать.
- `cap-*` не выделяется в отдельный файл — это раздел внутри `cmp-`. Ссылка из сценария: `-> cmp-<slug>/cap-<name>`.

## 5. Проверка перед сохранением

Чек-лист для workflow-скиллов (evolve, apply-change):

1. **Слой определён.** Куда кладу — `01-requirements/`, `02-specifications/`, `03-codemap/` или `04-decisions/`?
2. **Содержимое соответствует слою.** Запреты из §2 применены.
3. **Ссылки идут снизу вверх.** Из этого файла не указаны slug'и нижележащих слоёв.
4. **Нет утечки реализации.** Проверь смысл, включая обычный текст: спецификация задаёт
   наблюдаемое поведение и взаимодействия, а не изменения исходников. API-пути и поля
   схем не считать утечкой реализации.
5. **Граница workflow соблюдена.** Для evolve — только разрешённые цели и содержание;
   нижние зависимости отложены, а не запланированы. Проверь также решения и служебные файлы.

Исправь нарушения перед выдачей. Неразрешённое предметное противоречие — блокер,
который нужно назвать пользователю; не считать такой результат готовым.
