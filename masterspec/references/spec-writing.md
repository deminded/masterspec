# Компактная и проверяемая спецификация

Применять при создании и правке требований и спецификаций. Правила сокращают повторения,
а не обязательства. Границы слоя — [layer-discipline.md](layer-discipline.md), состав артефакта —
его шаблон, проверки готовности — [verification-axes.md](patterns/verification-axes.md).

## Один факт — один владелец

- Записывай норму один раз у её владельца. В других местах ставь `-> slug/ID` и поясняй только
  местное применение. Не копируй пороги, формулы, политики или списки допустимых значений.
- Требование задаёт наблюдаемый результат; спецификация добавляет распределение обязанностей
  и контракт частей. Не пересказывай требование перед каждым шагом спецификации.
- В `api`/`data` структура принадлежит машинному сайдкару. Компаньон содержит только семантику,
  которую сайдкар не выражает. Ссылка на поле/операцию допустима; повтор её схемы — нет.
- Сохраняй стабильные `slug`, `AC-*`, `cap-*`, `OE-*` и существующие ID правил/шагов. Новую норму,
  на которую нужен отдельный адрес, помечай локальным ID; не вводи второй реестр этих ID.

## Короткая норма с проверяемым исходом

Один пункт — одно обязательство: **условие → действие или результат → граница/исключение**,
если они применимы. Называй действующего субъекта и объект прямо; используй термин из глоссария.
Разделяй независимые обязательства. Не дроби одно условие на фразы, потеряв область действия.

- Пиши «Система отклоняет повторную заявку», а не «должна осуществлять корректную обработку».
- Для чисел указывай единицу, диапазон включительно/исключительно, окно и перцентиль, когда нужны.
  Значение берётся из входа; отсутствующее измерение нельзя заменить правдоподобным числом.
- Для каждого условия опиши исходы, включая отказ и «иначе». Для повторов и таймаутов задай
  наблюдаемый исход или сошлись на его владельца; фраза «обработать ошибку» не является исходом.
- Критерий приёмки: `AC-01: дано <состояние>, когда <действие>, тогда <наблюдаемый факт>`.
  Ссылайся на каноническую норму для общего порога; тестовая точка не создаёт вторую норму.

Пример для входного правила: «При количестве товаров больше 10 заявка отклоняется с причиной
„Превышен лимит“; иначе принимается». Его владелец — `rules-order/LIMIT-01`:

```text
Правило в функции: система принимает или отклоняет заявку по -> rules-order/LIMIT-01.
AC-01: дано 11 товаров, когда отправлена заявка, тогда показана причина «Превышен лимит»
       и заявка не создана. Основание: -> rules-order/LIMIT-01.
```

Порог остаётся в правиле, а число 11 — конкретные тестовые данные. Если исходный запрос не
содержит порог или причину отказа, вместо этого примера нужен `OPEN`.

## Структура без пустого каркаса

- Копируй обязательные поля и разделы шаблона. Условный раздел включай только по условию,
  написанному в шаблоне; неподходящие варианты нотации удаляй. Все прочие разделы обязательны.
- Отсутствие сведений не означает неприменимость. Для обязательного, но неприменимого пункта
  оставляй одну строку `N/A — <предметная причина>`; для неизвестного — `OPEN` по форме ниже.
- Удаляй HTML-инструкции, заглушки, пустые строки таблиц и списки вида `-> ...`.
  В «Связи» оставляй реальные ссылки, которые ещё не записаны в теле. Если раздел обязателен,
  но дополнительных связей нет: «Дополнительных связей нет». Поведенческие ссылки остаются
  в шагах/правилах/участниках: переносить их только в «Связи» нельзя.
- Обзор, цель, результат и постусловие отвечают на разные вопросы. Не повторяй один факт в них;
  используй короткую локальную ссылку, если он уже сформулирован в этом артефакте.
- Таблица нужна для сопоставления полей или случаев; последовательность — для шагов. Не делай
  широкую таблицу ради одного абзаца и не добавляй пересказ сразу после таблицы или диаграммы.

Лимита слов нет: сложный контракт может быть длинным. Не сокращаются восемь OE и четыре поля
каждой грани для external-I/O, явные альтернативы/отказы, полные ветвления и матрицы состояний,
источники, schema-first и связи для проверки покрытия. У internal-only остаётся точная строка
`OE: N/A — internal-only`; классификация — по реальной границе I/O, не по удобству сокращения.

## Известно, неизвестно, решено

Факт должен иметь основание в переданном входе. Общий источник можно указать один раз для
нескольких норм; отдельная новая provenance-таблица для каждого предложения не нужна.

Неизвестное: `OPEN — <какой факт нужен>; кому: <роль>; блокирует: <норма/решение>`.
`status: draft` сам по себе не заменяет этот вопрос. Гипотеза помечается как гипотеза и не
становится обязательством до решения. Если источники противоречат друг другу, сохрани обе ссылки
и верни конфликт; не выбирай молча. Существующие `TC-TODO`/`MIGRATE-TODO` сохраняют свои гейты.

Перед отдачей проверь: нет ли у одного факта двух владельцев; можно ли проверить каждый исход;
не исчезли ли условия, отказы или обязательные связи при сокращении; виден ли каждый `OPEN`.
